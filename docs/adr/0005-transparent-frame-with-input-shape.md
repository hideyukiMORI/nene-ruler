# ADR 0005 — 枠は透明な 2 次元の窓。描いたものだけが見え、描いたものだけが触れる

- 状態: 受理
- 日付: 2026-10-15
- Issue: #2
- 影響する規則: ARC-004 / ARC-005 / ARC-011 / RS-002 / QLT-013。仕様 FR-002〜FR-006 / FR-009 / FR-010 / FR-017 / FR-018

## 文脈

初版の仕様（2026-09-27）は「枠の無い細長い窓に目盛を描き、初版は不透明」「横／縦を切り替える」「ダーク・ライトのテーマ」だった。
施主は 2026-10-15 に次を口述した。

- 線・文字・アンカー・ギア**以外は透明**にしたい。中身は素通しで、下のアプリをそのまま操作できること
- 物差しは **2 次元の枠**。四辺すべてに目盛。左上と右下の鉤括弧（アンカー）を掴んで伸縮する
- 線は描画より広い帯で掴めるようにして、線を掴むと移動する
- 色は **1 色**（単色アプリ）。設定モーダルでプリセットと `#RRGGBB` の直接入力。ダーク・ライトは設定モーダルの背景だけ
- 数字は線の中央に小さく sans-serif

透明窓の成立条件を、開発環境（クラウドの Linux コンテナ・Xvfb）で実測した（2026-10-15）。

| 確認したこと | 実測 |
| --- | --- |
| Xvfb（`-screen 0 400x300x24`）の visual | depth 32 の visual が 20 個ある。`xdpyinfo` で `depth: 32` を数えた |
| 拡張 | `Composite` / `RENDER` / `SHAPE` / `XFIXES` がある |
| 合成器 | `xcompmgr -n` が Xvfb の上で起動する（`apt-get install xcompmgr`） |
| cairo | `ImageSurface` は既に ARGB32（ADR 0002）。背景を描かなければアルファ 0 のまま |

施主の実機は WSLg（XWayland ＋ Weston）で、Weston が合成器として `_NET_WM_CM_S0` を所有する。

## 決定

**枠の窓は 32 ビット ARGB の visual に作り、背景を描かず、XFixes の入力 shape で「描いたものの帯」だけをクリック可能にする。合成器が無ければ不透明に落ち、落ちたことを示す。向きとテーマは仕様から外し、色はインク色 1 つにする。**

1. **窓**: `TrueColor` / depth 32 の visual と専用の colormap で `CreateWindow`。`border_pixel = 0`・`background_pixel = 0`（透明）。WM の管理は変えない（FR-001・ADR 0002 の 2）
2. **描画**: `ImageSurface`（ARGB32・premultiplied）に、インク色でアルファ 1 の線・目盛・数字・鉤括弧・ギアだけを描く。`PutImage`（ZPixmap・depth 32）で転送する（ADR 0002 の 4）
3. **当たり判定**: core が物理画素で「触れる矩形の集合」（線の帯・アンカー・ギア・数字）を計算し、ui-x11 が `XFixesCreateRegion` → `XFixesSetWindowShapeRegion(ShapeInput)` に写す。中身の矩形は入力 shape に**含めない**ので、クリックは下の窓へ届く
4. **操作**: 線の帯で `ButtonPress` → `_NET_WM_MOVERESIZE`（`_NET_WM_MOVERESIZE_MOVE`）。アンカーで `ButtonPress` → `_NET_WM_MOVERESIZE`（`SIZE_TOPLEFT` / `SIZE_BOTTOMRIGHT`）。対応しない WM では自前の `ConfigureWindow` に落ちる（ADR 0002 の 3）
5. **合成器の検出**: 起動時に `_NET_WM_CM_S0`（画面 0）の `GetSelectionOwner`。所有者が無ければ、同じ `ImageSurface` の背景をインク色の補色（明るさで黒か白）で塗って不透明にし、FR-014 の経路で示す。透明にできるかどうかは `Transparency`（閉じた `enum`）として application が持つ
6. **仕様の改訂**: FR-006（向き）を撤回。FR-010 の「テーマ」を「インク色」と「モーダルの見え」に分ける。FR-017（透明と当たり判定）・FR-018（単色）を足す。`Orientation` / `ThemePalette` は作らない

## 強制

- **active**: 依存の許可制（ARC-013）。XFixes と Shape は `x11rb` の feature であり、新しい crate は要らない。`unsafe` は `unsafe_code = "forbid"`
- **active**: 画素の列の単体テスト。「背景のアルファが 0」「線の上のアルファが 255 でインク色」を X 無しで検証する（QLT-013 の実現手段）
- **planned**: 当たり判定の矩形が描いたものと一致すること。core の矩形計算と ui-x11 の描画が同じ `RulerFrame` を読むことで経路を 1 本にする（ARC-001）が、一致そのものはレビュー事項
- **planned**: 合成器の無い環境での不透明への降格。Xvfb 上で `xcompmgr` を止めた状態の PNG を gate-proofs に記録してから active と書く

## 結果

得られるもの:

- 物差しが「画面に描いた線」になる。下のアプリの文字や画像を遮らず、中身をクリックすれば下のアプリが反応する
- 色が 1 つなので配色表・テーマ切替・システム追従の実装が消える。設定は色・単位・最前面・モーダルの見えだけ
- 向きが消えるので `Orientation` と、向きごとの座標の入れ替えが消える。幅と高さの 2 つの `Length` が対称に並ぶ

失うもの・残る穴:

- **合成器が無い X では透明にならない。** Xorg 単体（コンポジタ無しの WM）では不透明に落ちる。落ちたことは示すが、透明に「する」手段は無い
- 単色なので、インク色と同じ色の背景（白い線を白い紙の上）では線が消える。縁取りは非要件（第 3 節）。必要になったら設定に足す
- 入力 shape は矩形の集合なので、鉤括弧の腕の形どおりには切れない。腕を含む矩形で近似する
- `_NET_WM_MOVERESIZE` の対応は WM 次第。WSLg（Weston の XWM）での動作は施主の目視で確かめる（QLT-013）
- 透明領域の `Expose` は合成器が担うが、WM によっては窓の再構成時に全体の再描画が要る。`ConfigureNotify` ごとに全体を描き直す

**正直に記録しておくこと:** 本 ADR は Xvfb の visual・拡張・合成器の起動までしか実測していない。窓が透明に出ることは Issue #2 の PNG で、WSLg で透明に出ることは施主の目視で実測する。

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| Shape の **bounding** 領域で窓そのものを線の形に切る | 合成器が無くても透明に見える利点はあるが、アンチエイリアスが効かず（矩形の集合）、1 px の線と 9 px の斜めの文字が階段になる。入力 shape だけを使い、見た目はアルファに任せる |
| 4 本の線を 4 つの窓にする | 移動・伸縮で 4 窓を同期させる状態が増え、ARC-004 の「所有者 1 つ」に反する。数字とアンカーの置き場も曖昧になる |
| `_NET_WM_WINDOW_OPACITY` で窓全体を半透明にする | 窓全体の透明度であって、描いたものと描いていないものを分けられない |
| override-redirect の窓で WM を迂回する | ADR 0002 で却下済み。フォーカス・重なり順・Snap を失う |
| 透明の代わりにキーカラー（特定の色を透過扱い） | X11 にその仕組みは無い。合成器が要ることは同じ |
| テーマ（ダーク・ライト）を枠にも残す | 透明な枠に「背景の配色」は存在しない。線の色が 1 つあれば足りる（施主の決定） |
