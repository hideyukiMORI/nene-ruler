# ADR 0029 — 論理画素の比は、定規の窓が乗っているモニタの dpi に従う

- 状態: 受理
- 日付: 2026-10-20
- Issue: #104
- 影響する規則: ARC-004 / ARC-007 / ARC-011。仕様 FR-008 / FR-016。ADR 0027 の決定 4（比は起動時に一度だけ）を置き換える。ADR 0021 の決定 2 の dpi の読み方（主モニタ）を Windows の起動時の値に限る

## 文脈

論理画素の比（dpi / 96）は起動時に一度だけ、主モニタの dpi から決めていた（ADR 0027 の決定 4）。
施主の実測（2026-10-20）: 主モニタ 125%、他のモニタ 150% と 175%。主モニタで起動して他のモニタへ動かすと、
`Logical px` の数字がブラウザの開発者ツールと合わない。125% のモニタでは合う。比が 1.25 のままなので、
150% のモニタでは開発者ツールの 1.2 倍、175% では 1.4 倍の数字が出ていた。

プロセスは per-monitor v2 の dpi 対応（ADR 0021）なので、窓がモニタをまたぐと Windows は `WM_DPICHANGED` を送る
（wparam の下位語が新しい dpi、lparam が推奨の矩形）。読んでいなかった。
ブラウザも同じ仕組みで、窓が乗っているモニタの dpi から `devicePixelRatio` を決める。

X11 の `Xft.dpi` は画面全体で 1 つで、ブラウザもそれしか見ない。モニタごとの dpi は無い。

## 決定

**比は定規の窓が乗っているモニタの dpi に従う。Windows は窓を作った直後に `GetDpiForWindow` で読み、`WM_DPICHANGED` が来るたびに取り直す。枠は選んだ単位の大きさを保つ（論理画素なら物理画素で伸縮し、物理画素ならそのまま）。飾りの整数倍率は変えない。**

1. `RulerIntent::DpiChanged(Option<u32>)` を足す。`RulerController` は比 `DevicePixelRatio` を持ち替え、次のフレームから数字の綴り（ADR 0027）・字の大きさと目盛（ADR 0028）・モーダルの説明文が新しい比に従う。比の所有者は application のまま（ARC-004）
2. ui-win32 は窓を作った直後に `GetDpiForWindow` を読んで `DpiChanged` を送り、`WM_DPICHANGED` では wparam の下位語を送る（0 なら `None`）。推奨の矩形は使わず `LRESULT(0)` で答える: 枠の大きさは測った値で、Windows の勧めで伸縮させない。モーダルが開いていれば説明文も描き直す
3. **枠は選んだ単位の大きさを保つ。** 施主の実測（2026-10-20）: 物理画素のまま保つと、`Logical px` の数字がまたぐたびに 320 → 228.6 → 266.7 と変わった。論理画素で測っている人にとって枠の大きさは論理画素の値であり、ブラウザの窓がモニタをまたぐとき物理的に伸縮するのと同じに振る舞うべきである。`RulerController::follow_dpi` は、論理画素を選んでいれば枠を `DevicePixelRatio::rescale`（物理画素 × 新 dpi / 旧 dpi・四捨五入・画面に収める）で伸縮し、物理画素を選んでいればそのままにする
4. **Windows の勝手な伸縮は打ち消す。** 施主の実測で、`Physical px` でもモニタをまたぐと数字が数 px 変わった。per-monitor v2 の窓は DPI が変わると Windows が非クライアント領域（`WS_THICKFRAME`）を再計算して窓を数 px 伸縮させる。`WM_GETDPISCALEDSIZE`（変わる直前）でいまの大きさを覚えて「このまま」と答え（SIZE に書いて TRUE）、`WM_DPICHANGED` では覚えた大きさを `WindowResized` で状態に戻してから `DpiChanged` を当て、状態が決めた窓の大きさに `SetWindowPos`（位置と重なり順は変えない）で合わせる。`SetWindowPos` が同期で届ける `WM_SIZE` は状態を借りている最中なので既定へ流れ、枠の大きさは `WindowResized` を直接当てて合わせる
5. 起動時の `Environment::desktop_dpi`（主モニタ・ADR 0021）は UI の整数倍率（飾り・ADR 0011）の元としてそのまま残す。倍率は起動時に一度だけ（窓の余白が変わるので、変えるなら別の Issue）
6. X11 は変えない。`DpiChanged` を送る所が無い

## 強制

- **active**: core の単体テスト（`rescale` の 120 → 168 dpi で 400 → 560、往復、144 → 168 で 467、`u16::MAX`）、application の単体テスト（120 dpi で起動して `Logical px` の 400 px が `320 logical px`、`DpiChanged(Some(168))` で枠が 560 × 336 になり `320 logical px` のまま・字が 16 / 19・説明文が `1 logical px = 1.75 physical px`・整数倍率は 1x のまま、`DpiChanged(None)` で 320 物理画素、`Physical px` では枠も数字も変わらない、画面より大きくならない）
- **active**: ui-win32 は `cargo clippy --target x86_64-pc-windows-gnu -- -D warnings` が 0 件
- **planned**: 施主の 3 モニタ（125% / 150% / 175%）で、動かすと説明文が変わり、`Logical px` の数字はまたいでも変わらず枠が物理的に伸縮して開発者ツールと合うこと、`Physical px` の数字もまたいでも変わらないこと（QLT-013）。記録は gate-proofs 第 51 節

## 結果

得られるもの:

- 倍率の違うモニタへ動かしても、論理画素の数字は変わらず（枠が物理的に伸縮する）、目盛・字の大きさがそのモニタのブラウザと合う
- 倍率を設定で変えたときも（Windows が同じ `WM_DPICHANGED` を送る）追従する

失うもの・残る穴:

- 飾り（鉤括弧・ギア・帯・目盛の長さ）の整数倍率は起動時のまま。125% で起動して 200% のモニタへ動かすと、字と目盛は 2 倍、飾りは 1 倍
- 窓が 2 つのモニタにまたがる間は、Windows が「より多く乗っている方」と判断した dpi
- 論理画素の大きさが整数でないとき（150% の 400 px = 266.7）、伸縮の丸めで最後の桁が 0.1〜0.2 動くことがある（144 → 168 dpi で 266.7 → 266.9）。往復しても元の物理画素には戻らないことがある
- X11 は `Xft.dpi` が 1 つなので、モニタごとの倍率には追従しない（ブラウザも同じ）

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| 比は起動時のまま、使う人に「測るモニタで起動する」よう求める | 施主の実測で外れた。主モニタで起動して別のモニタで測るのが普通の使い方 |
| `WM_DPICHANGED` の推奨の矩形で窓を伸縮する | 物理画素を選んでいるときは、測った 400 px が 480 px になって困る。論理画素のときは同じ結果になるが、Windows の推奨は位置も動かし、非クライアント領域の再計算も混ざる。伸縮は状態（`follow_dpi`）が単位に従って決め、UI はそれに合わせる方が経路が 1 本（ARC-001） |
| 単位に関わらず枠の物理画素を保つ（最初の実装） | 施主の実測で `Logical px` の数字が 320 → 228.6 → 266.7 と変わった。論理画素で測っている人には枠の大きさが変わったのと同じ |
| 飾りの整数倍率も `WM_DPICHANGED` で切り替える | 窓の余白（帯とギア）が変わり、窓の大きさを変えて枠の大きさを保つ扱いが要る。字と目盛の追従だけで実用上は足りる。要るなら別の Issue |
| 描くたびに `GetDpiForWindow` を読む | 描画が Win32 を読む経路になり、ARC-007（環境を読める場所）と ARC-011（UI は描くだけ）から外れる。メッセージで意図にするのが正典 |
